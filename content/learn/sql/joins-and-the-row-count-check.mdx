A join combines rows from two tables using a shared key. The syntax takes ten minutes to learn. The failure modes take longer, and they're what this lesson is really about.

## The four you need

```sql
SELECT s.invoice_no, c.customer_name
FROM sales s
INNER JOIN customers c ON s.customer_id = c.customer_id;
```

- **`INNER JOIN`** keeps rows that match in both tables. Anything unmatched disappears from both sides.
- **`LEFT JOIN`** keeps every row from the left table; unmatched right-side columns come back `NULL`.
- **`RIGHT JOIN`** is the mirror image, and is rare in practice — most people reorder the tables and use `LEFT` instead, because reading a query is easier when the driving table comes first.
- **`FULL OUTER JOIN`** keeps everything from both sides. Useful for reconciliation, where "what's in the ledger but not the bank statement" is exactly the question.

## The silent failure

`INNER JOIN` drops unmatched rows without telling you. If 40 of your 4,000 sales rows reference a customer ID that isn't in the customer table, your revenue total is quietly short by those 40 rows, and the query returns successfully.

This is the single most common way SQL reports go wrong. It doesn't error. It just under-reports.

So build this habit: **count before and after every join.**

```sql
SELECT COUNT(*) FROM sales;                    -- 4000

SELECT COUNT(*)
FROM sales s
INNER JOIN customers c ON s.customer_id = c.customer_id;   -- 3960
```

Forty rows vanished. Now go find out why — usually orphaned keys, sometimes a type mismatch where one side stores the ID as text.

To see exactly which rows are the problem, switch to a `LEFT JOIN` and filter for the nulls:

```sql
SELECT s.*
FROM sales s
LEFT JOIN customers c ON s.customer_id = c.customer_id
WHERE c.customer_id IS NULL;
```

## The other failure: rows multiplying

The opposite problem is more alarming and easier to spot. If your join key isn't unique in the right-hand table, rows multiply. Join 4,000 sales to a customer table where three customers appear twice, and you get more than 4,000 rows — with revenue double-counted for those customers.

Same check catches it. If the count goes *up* after a join, your key isn't unique on one side. Confirm with:

```sql
SELECT customer_id, COUNT(*)
FROM customers
GROUP BY customer_id
HAVING COUNT(*) > 1;
```

## Filtering in ON versus WHERE

With `INNER JOIN` these are equivalent. With `LEFT JOIN` they are not, and the difference surprises people:

```sql
-- Keeps all sales; only joins refunds from 2026.
LEFT JOIN refunds r
  ON s.invoice_no = r.invoice_no
  AND r.refund_year = 2026

-- Silently becomes an INNER JOIN: rows with no refund
-- have NULL refund_year, and NULL = 2026 is not true.
LEFT JOIN refunds r ON s.invoice_no = r.invoice_no
WHERE r.refund_year = 2026
```

Conditions on the *joined* table belong in `ON`. Conditions on the *driving* table belong in `WHERE`.

## Practice

Using the practice database:

1. Sales with customer names, and the count of sales rows that have no matching customer
2. Every customer with their total revenue, including those who bought nothing
3. Products that have never been sold
4. A sales-and-refunds view where sales without refunds still appear

Number 2 and number 4 both require `LEFT JOIN`. If you get an inner join's row count, re-read the section above.
